# План разработки: Анализатор рисков оттока

Команда: **BE-1** (ядро данных и модель), **BE-2** (API и платформа), **FE** (фронтенд).
Стек: Django + DRF, PostgreSQL, React (Vite), Docker Compose, Prometheus-метрики, SSE для живого обновления.

> Документ опирается на текст кейса. В PDF много опечаток (`/metics`, `pice`, `pefomed`, `quater_year`, `paymentTem`). **Первым делом сверьте имена полей с реальными файлами по ссылке из кейса** и поправьте контракты ниже.

## 1. Принятые архитектурные решения

| Вопрос                 | Решение                                                                                             | Почему                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Происхождение запросов | Один origin: nginx раздаёт React-билд и проксирует `/api`, `/metrics` на backend                    | Нет проблем с CORS/CSRF/cookie, проще для жюри                              |
| Аутентификация         | Django-сессии (`SessionAuthentication`) + CSRF                                                      | Просто, соответствует требованию «логин и пароль»                           |
| `/metrics`             | Bearer-токен из env (`METRICS_TOKEN`)                                                               | Prometheus не умеет логиниться формой, а открытым эндпоинт оставлять нельзя |
| Живое обновление       | SSE (`GET /api/v1/events`)                                                                          | Проще WebSocket, достаточно односторонней отправки                          |
| Настройки модели       | Одна запись в БД (JSON)                                                                             | Переживает рестарт                                                          |
| Расчёт                 | Пересчёт всех клиентов при смене настроек или снимка, результат кладётся в таблицу `RiskAssessment` | Быстрые списки и сортировки, метрики согласованы с UI                       |
| Расширяемость          | Реестр признаков (decorator), веса хранятся в настройках, UI настроек строится из схемы             | Новый признак = одна функция                                                |
| Деньги                 | Все суммы в API в «единицах баланса» (`*_cents`, 100 = €1); форматирует фронт                       | Нет ошибок округления                                                       |

## 3. Контракты API (согласовать до начала работы, это главный стык команд)

Все эндпоинты, кроме `auth/login` и `/metrics` (там свой токен), требуют сессии. Ошибки в едином формате: `{"detail": "...", "code": "..."}`.

### 3.1. Формат снимка исходных данных (`PUT /api/v1/source/snapshot`)

Финальную форму определяют реальные файлы. Рабочая гипотеза:

```json
{
  "accounts": [
    {"id": 1, "email": "a@b.c", "balance": 12000, "withdrawBalance": 0,
     "bonusBalance": 500, "bonusState": true, "totalReplenished": 50000}
  ],
  "services": [
    {"id": 10, "accountId": 1, "name": "VPS-1", "status": "active",
     "price": 30000, "autoprolong": false, "paymentTerm": "month",
     "expiresAt": "2026-11-01T00:00:00Z"}
  ],
  "transactions": [
    {"id": 100, "accountId": 1, "status": "performed", "type": "prolong", "amount": 30000}
  ]
}
```

Ответ: `{"accounts": N, "services": N, "transactions": N, "recalculated_at": "..."}`.
Загрузка заменяет данные целиком, в одной транзакции БД (при ошибке валидации ничего не меняется).

### 3.2. `GET /api/v1/customers`

Параметры: `level` (`high|medium|low|none`), `search` (по email), `ordering` (`id`, `email`, `balance`, `total_replenished`, `score` с префиксом `-` для убывания), `page`, `page_size`.

```json
{
  "count": 120, "page": 1, "page_size": 25,
  "results": [
    {"id": 1, "email": "a@b.c", "balance_cents": 12000,
     "total_replenished_cents": 50000,
     "score": 78.5, "level": "high",
     "top_reason": "Услуга истекает через 2 дня, автопродление выключено",
     "expected_loss_cents": 23500}
  ]
}
```

Если данных для оценки недостаточно: `"score": null, "level": "none", "top_reason": "Недостаточно данных для оценки"`.

### 3.3. `GET /api/v1/customers/{id}`

```json
{
  "id": 1, "email": "a@b.c",
  "balance_cents": 12000, "bonus_balance_cents": 500, "bonus_usable": true,
  "withdraw_balance_cents": 0, "total_replenished_cents": 50000,
  "score": 78.5, "level": "high",
  "expected_loss_cents": 23500,
  "factors": [
    {"key": "expiring_no_autoprolong", "title": "Скоро истекает без автопродления",
     "value": 1.0, "weight": 40, "contribution": 40.0,
     "explanation": "VPS-1 истекает 01.11.2026, автопродление выключено"}
  ],
  "services": [
    {"id": 10, "name": "VPS-1", "status": "active", "price_cents": 30000,
     "payment_term": "month", "autoprolong": false, "expires_at": "...",
     "days_to_expiry": 8, "monthly_equivalent_cents": 30000,
     "expected_loss_cents": 23500}
  ]
}
```

### 3.4. `GET /api/v1/analytics/summary`

```json
{
  "calculated_at": "2026-10-24T10:00:00Z",
  "customers_total": 120,
  "by_level": {"high": 14, "medium": 31, "low": 70, "none": 5},

}
```

Для графика (дополнительная функция): `GET /api/v1/analytics/churn-chart?days=30`

```json
{"series": [
  {"date": "2026-10-20", "kind": "fact", "deleted_services": 3, "services_at_risk": 40},
  {"date": "2026-10-26", "kind": "forecast", "expected_non_renewals": 5, "services_at_risk": 42}
]}
```

### 3.5. `GET|PATCH /api/v1/model/settings`

```json
{
  "weights": {"expiring_no_autoprolong": 40, "insufficient_funds": 30, "prolong_wait": 20},
  "thresholds": {"medium": 35, "high": 65},
  "params": {"expiry_horizon_days": 7, "use_bonus_balance": true, "loss_horizon_months": 1},
  "schema": {
    "weights": [{"key": "expiring_no_autoprolong", "title": "...", "description": "...", "min": 0, "max": 100}]
  }
}
```

`PATCH` принимает частичный объект, валидирует (веса ≥ 0, `medium < high`), сохраняет, запускает пересчёт и шлёт SSE-событие. `schema` позволяет фронту нарисовать форму без хардкода признаков.

### 3.6. Аутентификация

| Метод | Путь | Поведение |
|---|---|---|
| POST | `/api/v1/auth/login` | `{username, password}` → 200 + cookie сессии, 400/401 при ошибке |
| GET | `/api/v1/auth/me` | 200 `{id, username}` или 401/403 |
| POST | `/api/v1/auth/logout` | 204, сессия сброшена |
| GET | `/api/v1/auth/csrf` | выставляет cookie `csrftoken` (нужен SPA до первого POST) |

### 3.7. SSE: `GET /api/v1/events`

Событие `recalculated`, данные: `{"reason": "settings|snapshot", "at": "...", "summary": {...}}`. Каждые 15 секунд `: ping`, чтобы соединение не рвалось прокси.

## 4. Модель оценки риска (предложение, команда может изменить и обязана кратко объяснить жюри)

### 4.1. Нормализация

- Доступные средства клиента: `available = balance + (bonusBalance, если bonusState разрешает и включён параметр use_bonus_balance)`. `withdrawBalance` не учитывается как основной баланс (автопродление списывает с основного и бонусного), но может добавляться опциональным коэффициентом.
- Месячный эквивалент цены услуги: `hour ×730`, `week ×4.345`, `month ×1`, `quarter ÷3`, `half_year ÷6`, `year ÷12`.
- Вклад в риск учитывают услуги в статусах `active`, `suspended`, `prolong_wait`. `deleted` и `blocked` считаются уже потерянными/недоступными и в прогнозе не участвуют (удалённые попадают в график фактов).

### 4.2. Признаки (каждый возвращает значение 0..1 и текст причины)

| Ключ | Идея | Базовый вес |
|---|---|---|
| `expiring_no_autoprolong` | Услуга истекает в пределах `expiry_horizon_days`, автопродление выключено. Чем ближе дата, тем ближе значение к 1 | 40 |
| `insufficient_funds` | `available` меньше суммы ближайших продлений. Значение = доля непокрытой суммы | 30 |
| `prolong_wait` | Услуга в `prolong_wait`; усиливается, если средств не хватает | 20 |
| `low_payment_success` | Много `not_performed` транзакций от общего числа | 10 |

### 4.3. Формулы

```
score = clamp( Σ (weight_i × value_i) / Σ weight_i × 100, 0, 100 )
level = high   если score ≥ thresholds.high
        medium если score ≥ thresholds.medium
        low    иначе
level = none   если у клиента нет услуг в учитываемых статусах (недостаточно данных)

probability = score / 100
expected_loss(customer) = probability × Σ monthly_equivalent(service) × loss_horizon_months
revenue_at_risk = Σ monthly_equivalent услуг клиентов с level ∈ {medium, high}
```

Денежная оценка явно учитывает: стоимость услуг (`price`, `paymentTerm`), балансы (через признак `insufficient_funds` и покрытие), риск (`probability`). Это и нужно показать в пояснении на панели.

### 4.4. Расширяемость

```python
# analytics/features/registry.py
FEATURES: dict[str, Feature] = {}

def feature(key, title, default_weight, description=""):
    def deco(fn):
        FEATURES[key] = Feature(key, title, default_weight, description, fn)
        return fn
    return deco

# analytics/features/expiring.py
@feature("expiring_no_autoprolong", "Скоро истекает без автопродления", 40)
def expiring(ctx: CustomerContext, params) -> FeatureResult:
    ...
    return FeatureResult(value=0.8, explanation="VPS-1 истекает через 2 дня")
```

Новый признак: создать файл с функцией и импортировать его в `features/__init__.py`. Вес по умолчанию появится в настройках, в схеме настроек и в UI автоматически. Эту процедуру описать в README.

### BE-1: Ядро данных и модель риска

#### B1.1. Модели данных источника
**Требования:**
- Модели `Customer` (account), `Service`, `Transaction` с полями из кейса. Денежные поля `BigIntegerField` (единицы баланса).
- `Service.status` и `payment_term` как `TextChoices`, `Transaction.status`/`type` аналогично.
- Индексы по `customer_id`, `status`, `expires_at`.
- Миграции применяются на чистой БД без ошибок.

**Готово, когда:** модели создаются в админке, миграции проходят в Docker.

#### B1.2. Сервис импорта снимка
**Требования:**
- Функция `replace_snapshot(payload) -> ImportResult` в одной транзакции (`atomic`): очистка и полная замена данных.
- Валидация: обязательные поля, типы, допустимые значения статусов, ссылочная целостность (`accountId` существует), понятные сообщения об ошибках с путём к полю.
- Устойчивость к дублям ID и пустым спискам.
- Перед заменой диффит статусы услуг и записывает `ServiceStatusEvent` (услуга, старый статус, новый статус, время). Это источник «фактов» для графика, так как исторических дат в данных нет.
- После успешной загрузки вызывает `recalculate_all(reason="snapshot")`.

**Готово, когда:** юнит-тесты на успех, невалидный снимок (БД не изменилась) и повторную загрузку.

#### B1.3. Тестовые и расширенные данные
**Требования:**
- Скрипт загрузки исходного набора из кейса (`manage.py load_sample`).
- Расширенный набор для демонстрации: клиенты на каждом уровне риска, без услуг (`none`), с `prolong_wait` и пустым балансом, с бонусным балансом при `bonusState=false`, с почасовой оплатой.
- Положить в `sample-data/`, описать в README.

#### B1.4. Реестр признаков и движок оценки
**Требования:**
- Реестр из раздела 4.4, `CustomerContext` (клиент, услуги, транзакции, текущее время, параметры).
- `scoring.compute(ctx, settings) -> Assessment` (score, level, factors[], probability).
- Текущее время передаётся параметром (для тестов).
- Обработка пустых данных: уровень `none`, score `null`.
- Каждый фактор отдаёт `explanation` на русском с конкретными значениями (услуга, даты, суммы).

#### B1.5. Реализация признаков
**Требования:** четыре признака из 4.2, каждый в своём файле, с юнит-тестами на граничные случаи (ровно на пороге горизонта, нулевой баланс, бонус недоступен, `autoprolong=true` при достаточных средствах → признак ≈ 0).

#### B1.6. Денежная оценка
**Требования:**
- `monthly_equivalent(price, payment_term)`.
- `expected_loss` по клиенту и по услуге, `revenue_at_risk`, `services_at_risk`.
- Сумма по услугам клиента совпадает с суммой клиента, сумма по клиентам совпадает с итогом `summary` (тест на согласованность).
- Текстовое пояснение формулы отдаётся в `summary.explanation`.

#### B1.7. Модель настроек и персистентность
**Требования:**
- Singleton-модель `ModelSettings` (JSONField) с дефолтами из реестра. Новые признаки подхватываются без миграции данных.
- Валидация: `weights ≥ 0`, хотя бы один вес > 0, `0 ≤ medium < high ≤ 100`, допустимые диапазоны параметров.
- Метод `get_schema()` для UI.

#### B1.8. Сервис пересчёта
**Требования:**
- `recalculate_all(reason)`: считает всех клиентов (bulk), пишет в `RiskAssessment` (клиент, score, level, probability, factors JSON, expected_loss, calculated_at) и в `AnalyticsSnapshot` (агрегаты для summary и `/metrics`).
- Выполняется в транзакции, потокобезопасно (блокировка/advisory lock, чтобы два пересчёта не затёрли друг друга).
- По завершении вызывает хук `on_recalculated` (его использует BE-2 для SSE).
- Укладывается в секунды на расширенных данных (тысячи клиентов).

#### B1.9. Тесты и документация модели
**Требования:** `pytest`, покрытие ядра, `docs/model.md` (признаки, формулы, коэффициенты, пороги, обоснование выбора для жюри, как добавить признак).

### BE-2: API и платформа

#### B2.1. Каркас проекта и окружение
**Требования:**
- Приведённый `settings.py` (из чата), `.env.example`, `requirements.txt`.
- Структура приложений по разделу 2, `/health` для проверки контейнера.
- `ruff`/`black` по желанию, единые настройки.

#### B2.2. Аутентификация
**Требования:**
- Эндпоинты из 3.6, форма ошибок единая.
- Эндпоинт `csrf`, `login` защищён от перебора (простой throttle DRF, например 10/мин на IP).
- Создание администратора при старте контейнера из `ADMIN_USERNAME`/`ADMIN_PASSWORD` (идемпотентно), данные для входа описаны в README.
- По умолчанию `IsAuthenticated`; публичными явно помечены только `login` и `csrf`.

**Готово, когда:** запрос к любому `/api/v1/*` без сессии возвращает 401/403 (тест на каждый эндпоинт).

#### B2.3. `GET /api/v1/customers`
**Требования:**
- Фильтры `level`, `search`; сортировка по `id`, `email`, `balance`, `total_replenished`, `score` в обе стороны; пагинация.
- Сортировка по `score` с `NULL` в конце при обоих направлениях.
- Запрос выполняется без N+1 (`select_related`), проверка `assertNumQueries`.
- Ответ строго по контракту 3.2.

#### B2.4. `GET /api/v1/customers/{id}`
**Требования:** контракт 3.3, 404 для несуществующего клиента, факторы отсортированы по вкладу, услуги содержат `days_to_expiry` и вклад в потери.

#### B2.5. `GET /api/v1/analytics/summary` и данные графика
**Требования:**
- Summary по 3.4 читается из `AnalyticsSnapshot` (не пересчитывает на лету).
- `churn-chart`: факты из `ServiceStatusEvent` и текущего числа `deleted`, прогноз по услугам с `expires_at` в окне и высоким риском; в ответе чётко разделены `kind: fact|forecast`.

#### B2.6. `GET|PATCH /api/v1/model/settings`
**Требования:** контракт 3.5, `PATCH` частичный, ошибки валидации понятные (400 с указанием поля), после сохранения вызывается `recalculate_all("settings")`, ответ возвращает уже действующие настройки. Настройки видны после рестарта контейнера.

#### B2.7. `PUT /api/v1/source/snapshot`
**Требования:** тонкая обёртка над `replace_snapshot` из B1.2, лимит размера тела, 400 с детализацией ошибок, ответ по 3.1. Поддержать загрузку и JSON-телом, и `multipart` файлом (для кнопки в UI) по желанию.

#### B2.8. Живое обновление (SSE)
**Требования:**
- Эндпоинт `/api/v1/events` по 3.7, требует сессию.
- Хук `on_recalculated` публикует событие всем подписчикам. Для нескольких воркеров использовать Postgres `LISTEN/NOTIFY` или простой общий канал (Redis не обязателен, если воркер один).
- Запуск через ASGI (`uvicorn`) или `gunicorn -k gthread`, чтобы стрим не блокировал остальные запросы.
- Заголовки `Cache-Control: no-cache`, `X-Accel-Buffering: no` (для nginx).

**Готово, когда:** `curl -N` показывает событие после `PATCH` настроек.

#### B2.9. `GET /metrics`
**Требования:**
- Формат Prometheus (`prometheus_client`), доступ по `Authorization: Bearer <METRICS_TOKEN>`.
- Метрики: `churn_customers{level="high|medium|low|none"}`, `churn_expected_loss_cents`, `churn_revenue_at_risk_cents`, `churn_services_at_risk`, `churn_score_avg`, `churn_last_recalculation_timestamp`.
- Значения берутся из того же `AnalyticsSnapshot`, что и `summary` (тест на равенство).

#### B2.10. OpenAPI и Swagger
**Требования:** `drf-spectacular`, Swagger UI на `/api/v1/docs`, описания, примеры и схемы ответов для каждого эндпоинта, файл `backend/openapi.yml` выгружен (`manage.py spectacular --file openapi.yml`) и закоммичен. Все обязательные эндпоинты из кейса присутствуют.

#### B2.11. Docker, nginx, README
**Требования:**
- `docker-compose.yml`: `db` (с healthcheck), `backend` (миграции и `collectstatic` в entrypoint, ожидание БД), `frontend` (nginx + билд React, проксирует `/api` и `/metrics`, SSE без буферизации). Опционально `prometheus` с готовым `prometheus.yml`.
- Том для данных PostgreSQL, чтобы настройки переживали перезапуск.
- README: запуск одной командой, учётные данные, как загрузить данные, адреса (панель, Swagger, metrics), описание модели и архитектуры, как добавить признак, переменные окружения.
- Проверка: `docker compose down && docker compose up` на чистой машине.

#### B2.12. OIDC (дополнительно, после обязательного)
**Требования:** вход через OIDC (`mozilla-django-oidc` или `authlib`), провайдер настраивается через env (Keycloak в compose по желанию), опциональный fallback на логин/пароль, пометка в UI «Войти через SSO». Включается флагом `OIDC_ENABLED`.

### FE: Фронтенд (React)

#### F1. Каркас и API-слой
**Требования:**
- Vite + React + TypeScript, React Router, TanStack Query (кэш и инвалидация).
- API-клиент: `credentials: "include"`, автоматическая подстановка `X-CSRFToken`, единая обработка 401 (редирект на логин).
- Типы ответов по контрактам раздела 3.
- **Моки (MSW)** по контрактам, чтобы работать независимо от backend с первого дня.
- Защищённые маршруты (`/`, `/customers`, `/customers/:id`, `/settings`, `/data`).

#### F2. Страница входа
**Требования:** форма логин/пароль, состояния загрузки и ошибки («Неверный логин или пароль»), блокировка кнопки при отправке, после входа редирект на исходную страницу, выход в шапке.

#### F3. Общий layout и навигация
**Требования:** боковое меню (Обзор, Клиенты, Модель, Данные), шапка с пользователем и индикатором «Обновлено в HH:MM» / «Нет связи», адаптивность для ноутбука и планшета, единые токены дизайна (цвета уровней: высокий красный, средний жёлтый, низкий зелёный, нет оценки серый).

#### F4. Обзор (дашборд)
**Требования:**
- Карточки: клиентов по уровням, услуг под риском, выручка под риском, ожидаемая потеря.
- Блок «Как считается сумма»: текст `explanation` с формулой и расшифровкой слагаемых.
- Топ-5 клиентов под риском со ссылкой на карточку.
- Скелетоны при загрузке, понятное пустое состояние.

#### F5. Таблица клиентов
**Требования:**
- Колонки: ID, email, баланс, сумма пополнений, score, уровень (бейдж), главная причина.
- **Сортировка по ID, email, балансу, сумме пополнений в обе стороны**, индикатор направления, сортировка по score.
- Фильтр по уровню, поиск по email, пагинация, состояние сортировки сохраняется в URL.
- Для `level=none` явно «Нет оценки» и пояснение, а не ноль.
- Форматирование денег из единиц баланса в евро (100 = €1).
- Клик по строке открывает карточку клиента.

#### F6. Карточка клиента
**Требования:** score и уровень крупно, список факторов с вкладом (горизонтальные полосы) и текстом причины, таблица услуг (статус, цена, период, автопродление, дней до окончания, ожидаемая потеря), денежная оценка клиента с пояснением, «назад к списку» с сохранением фильтров.

#### F7. Настройки модели
**Требования:**
- Форма строится **из `schema`** ответа `GET /model/settings` (новые признаки появляются без правок фронта).
- Слайдеры/поля для весов, порогов и параметров, валидация на клиенте (`medium < high`, веса ≥ 0), кнопки «Сохранить» и «Сбросить».
- После сохранения показывается статус «Пересчёт…» → «Готово», данные на других страницах обновляются без перезагрузки.
- Ошибки валидации с сервера отображаются у полей.

#### F8. Живое обновление
**Требования:** хук `useLiveUpdates` на `EventSource("/api/v1/events")`, при событии `recalculated` инвалидирует запросы summary, customers, customer detail, настроек; авто-переподключение при обрыве, индикатор состояния соединения в шапке; закрытие соединения при выходе из аккаунта.

#### F9. График оттока (дополнительно)
**Требования:** Recharts, оси по датам, **факт (сплошная линия) и прогноз (пунктир/другой цвет) визуально различимы**, легенда, подсказки, переключатель периода (14/30/90 дней), пустое состояние при отсутствии истории с пояснением.

#### F10. Страница «Данные»
**Требования:** загрузка JSON-снимка (drag-and-drop или выбор файла) → `PUT /source/snapshot`, предпросмотр (число аккаунтов, услуг, транзакций), отображение ошибок валидации списком, подтверждение «данные будут заменены полностью», результат и время пересчёта.

#### F11. UX-полировка
**Требования:** единые состояния загрузки/ошибки/пусто, доступные контрасты, клавиатурная навигация по таблице, подсказки (tooltip) над терминами (`prolong_wait`, `autoprolong`), тексты на русском, переключение тёмной темы по желанию.

#### F12. OIDC-кнопка (дополнительно)
**Требования:** кнопка «Войти через SSO» показывается, если backend сообщил о включённом OIDC (поле в `/auth/me` или `/auth/config`), логин/пароль остаётся как fallback.

## 6. Порядок работ и зависимости

```
Этап 0 (все): данные, контракты, формула
   │
   ├── BE-1: B1.1 → B1.2 → B1.4 → B1.5 → B1.6 → B1.7 → B1.8 → B1.3/B1.9
   ├── BE-2: B2.1 → B2.2 → (моки сервисов) B2.3/B2.4/B2.6/B2.7 → B2.5 → B2.8 → B2.9 → B2.10 → B2.11
   └── FE:   F1(+моки) → F2 → F3 → F5 → F4 → F6 → F7 → F8 → F10 → F9 → F11
                                                    │
Интеграция: после B1.8 + B2.3..B2.7 заменить моки реальным API
Затем:  B2.12 / F12 (OIDC)  →  демо-репетиция  →  заморозка
```

Ключевые точки синхронизации:
1. **Контракты утверждены** (S0.2): после этого FE работает на моках, BE-2 на заглушках сервисов.
2. **B1.2 + B1.4 готовы:** BE-2 подключает реальные данные и оценки.
3. **B1.8 + B2.8 готовы:** сквозное «изменил настройку → UI обновился сам».
4. **Интеграционный прогон** на чистом `docker compose up`.

## 7. Сквозной демо-сценарий (репетировать до защиты)

1. Войти в панель.
2. На «Обзоре» показать суммы риска и пояснение денежной оценки.
3. В таблице отсортировать по балансу, найти клиента с высоким риском.
4. Открыть карточку, показать причины (например, истекает через 2 дня, автопродление выключено, не хватает средств).
5. Открыть «Модель», изменить вес признака → без перезагрузки меняются score, рейтинг и деньги.
6. Загрузить новый снимок данных на странице «Данные» → всё обновляется само.
7. Показать `/metrics` (с токеном) и убедиться, что цифры совпадают с панелью.
8. Перезапустить контейнеры и показать, что настройки сохранились.
9. Показать Swagger и график оттока (факт и прогноз).

## 9. Риски

| Риск | Что делать |
|---|---|
| Реальные имена полей отличаются от опечаток в PDF | Закрыть в S0.1, держать маппинг в одном месте (`customers/importer.py`) |
| Нет истории статусов и дат удаления | `ServiceStatusEvent` накапливается из диффов снимков, на графике явно подписать, что факты копятся с момента запуска |
| SSE блокирует воркеры | ASGI или `gthread`, отдельный тест |
| Nginx буферизует SSE | `proxy_buffering off`, заголовок `X-Accel-Buffering: no` |
| Расхождение метрик и панели | Один источник (`AnalyticsSnapshot`) и тест на равенство |
| Два пересчёта одновременно | Advisory lock в `recalculate_all` |
| Слишком большой объём в срок | Сначала обязательные пункты, потом OIDC, график, полировка |

## 10. Definition of Done для каждой задачи

- Код в `main` через PR, ревью от коллеги.
- Тесты проходят (backend: `pytest`, frontend: хотя бы сборка и типы без ошибок).

- Нет секретов в репозитории, новые переменные добавлены в `.env.example`.
- Работает в `docker compose up` на чистом окружении.
