# Churn Risk Analyzer

Аналитическая панель для маркетологов хостинга Aéza. По данным аккаунтов, услуг и транзакций
она отвечает на три вопроса:

- **кому нужно внимание** — score риска оттока и уровень для каждого клиента;
- **почему** — признаки риска с конкретными услугами, датами и суммами;
- **сколько можно потерять** — ожидаемая потеря в евро по клиенту и по всем клиентам.

Коэффициенты модели настраиваются в панели. После изменения настроек или загрузки новых данных
оценки пересчитываются, и все открытые вкладки обновляются сами, без перезагрузки.

Развёрнутая версия: https://churn-risk.duckdns.org

## Быстрый старт

Нужны Docker и Docker Compose.

```bash
cp .env.example .env
docker compose up -d --build
```

Через минуту откройте http://localhost:8080 и войдите как `admin` / `admin`
(значения `DJANGO_SUPERUSER_USERNAME` и `DJANGO_SUPERUSER_PASSWORD` из `.env`).

При первом запуске база сама заполняется данными из кейса и демонстрационными клиентами:
всего 22 клиента. Данные и настройки модели хранятся в PostgreSQL на томе `pgdata` и переживают
перезапуск. Начать с чистой базы: `docker compose down -v`.

| Адрес | Что там |
|---|---|
| http://localhost:8080 | Панель |
| http://localhost:8080/api/v1/docs | Swagger |
| http://localhost:8080/api/v1/schema | OpenAPI-схема, она же в `backend/openapi.yml` |
| http://localhost:8080/metrics | Метрики в формате Prometheus, нужен токен |
| http://localhost:9090 | Prometheus, собирает `/metrics` (открыт только локально) |
| http://localhost:3000 | Grafana с дашбордом по метрикам, `admin` / `admin` (открыта только локально) |
| http://localhost:8080/admin | Django admin для разработчиков |

## Демонстрация за 5 минут

1. **«Обзор»**: ожидаемая потеря и блок «Как считается сумма».
2. **«Клиенты»**: сортировка по балансу и пополнениям, фильтр «Высокий».
3. **Клиент 101**: причины риска с датами и суммами, деньги клиента. Пары **104 / 105** и
   **102 / 103** отличаются одним условием, и видно, как меняется уровень.
4. **«Модель» во второй вкладке**: уменьшить вес «Ожидает оплаты» с 80 до 20 и сохранить —
   «Обзор» и карточка клиента в первой вкладке обновятся сами.
5. **«Данные»**: загрузить `sample-data/case.json` — панель обновится сама. Вернуть полный набор:
   `docker compose exec backend python manage.py load_sample --extended`.
6. **Prometheus** (http://localhost:9090): запрос `churn_expected_loss_cents` совпадает с суммой
   на «Обзоре» (в центах).
7. **Grafana** (http://localhost:3000): дашборд «Churn Risk Analyzer» открывается сразу после
   входа — ожидаемая потеря в евро, клиенты по уровням и их динамика после пересчётов из шагов 4–5.

## Данные

Формат совпадает с исходной системой (`test_data/data.json`, схема `test_data/001_schema.up.sql`).
Суммы — в единицах баланса, 100 = €1.

В `sample-data/` лежат два набора:

- `case.json` — набор из кейса без изменений: 10 клиентов, 30 услуг, 100 транзакций;
- `demo.json` — 12 демонстрационных клиентов (id 101–112), по одному на каждую ситуацию,
  которую ловит модель. Список сценариев — в [sample-data/README.md](sample-data/README.md).

Набор кейса снят на 19.10.2026 15:00 UTC. При загрузке все даты сдвигаются так, что эта точка
совпадает с текущим моментом: «услуга истекает через 2 дня» остаётся правдой в день демонстрации.

Чем заполнить пустую базу при старте, задаёт `SAMPLE_AUTOLOAD` в `.env`: `extended`
(по умолчанию, кейс и демо), `case` или `none`. Загрузить заново:

```bash
docker compose exec backend python manage.py load_sample --extended   # кейс и демо
docker compose exec backend python manage.py load_sample              # только кейс
```

Свой снимок загружается на странице «Данные» или через `PUT /api/v1/source/snapshot`.
Загрузка заменяет данные целиком в одной транзакции; если снимок не прошёл проверку, ничего
не меняется, а в ответе — список ошибок с путём к полю. Формат и ошибки описаны в
[docs/api-contract.md](docs/api-contract.md).

## Модель

Учитываются услуги, которые клиент ещё может продлить или потерять: `active`, `suspended`,
`prolong_wait`. Каждый признак даёт значение от 0 (причины нет) до 1 (проявилась полностью)
и текст причины.

| Признак | Основание в кейсе | Вес по умолчанию |
|---|---|---|
| Скоро истекает без автопродления | услуга заканчивается в ближайшие 7 дней, автопродление выключено | 70 |
| Не хватает средств на продления | основного и доступного бонусного баланса мало для ближайших продлений | 50 |
| Ожидает оплаты | услуга в статусе `prolong_wait`, тем сильнее, чем меньше денег | 80 |
| Неоплаченные транзакции | доля транзакций `not_performed` | 20 |

Вес — вероятность ухода в процентах, если причина проявилась полностью. Признаки считаются
независимыми причинами:

```
score = (1 − Π (1 − вес / 100 × значение)) × 100
```

Уровень: высокий от 65, средний от 35, ниже — низкий. Если у клиента нет действующих услуг,
оценки нет: «Недостаточно данных для оценки».

**Денежная оценка.** Ожидаемая потеря клиента = вероятность ухода (score / 100) × месячная
стоимость его услуг × горизонт потерь (по умолчанию 1 месяц). Тарифы с оплатой по часам,
неделям, кварталам и годам пересчитываются в месяц. Балансы учитываются через вероятность:
если денег не хватает на продления, риск растёт. Выручка под риском — стоимость услуг клиентов
со средним и высоким риском.

Веса, пороги уровней, горизонт прогноза, горизонт потерь и учёт бонусного баланса меняются на
странице «Модель». Подробно, с обоснованием формулы: [docs/model.md](docs/model.md).

### Как добавить признак

1. Создать модуль в `backend/analytics/features/` с функцией от `CustomerContext`, которая
   возвращает `FeatureResult(value, explanation)`, и обернуть её в
   `@feature(key, title, default_weight, description)`.
2. Импортировать модуль в `backend/analytics/features/__init__.py`.

Вес нового признака сам появится в настройках модели и в форме на странице «Модель»:
форма строится по схеме из `GET /api/v1/model/settings`. Миграции не нужны.

## Как устроено

```
браузер ─► nginx (frontend) ─┬─► статика React
                             ├─► /api, /metrics ─► Django + DRF (uvicorn) ─► PostgreSQL
                             └─► /kc ─► Keycloak (если включён SSO)
Prometheus ─► backend:8000/metrics
Grafana ─► Prometheus
```

```
backend/
  customers/   модели источника (аккаунты, услуги, транзакции), импорт и проверка снимка
  analytics/   признаки, расчёт score и денег, настройки модели, пересчёт
  api/         REST API, вход, SSE, /metrics, синхронизация пользователей с Keycloak
  config/      настройки Django, тема Django admin
frontend/      React + TypeScript + TanStack Query, Tailwind; графика из гайдбука Aéza
keycloak/      realm для SSO и тема страниц входа в стиле панели
monitoring/    конфиг Prometheus, источник данных и дашборд Grafana
sample-data/   наборы данных, test_data/ — исходные данные кейса
docs/          описание модели и контракты API
```

**Пересчёт.** Запускается после загрузки снимка и после сохранения настроек, в той же
транзакции. Результаты пишутся в `RiskAssessment` (по клиенту) и `AnalyticsSnapshot` (итоги).
Из `AnalyticsSnapshot` читают и панель, и `/metrics`, поэтому цифры совпадают.

**Живое обновление.** После пересчёта сервер отправляет событие `recalculated` в
`GET /api/v1/events` (Server-Sent Events). Панель держит это соединение открытым и при событии
перезапрашивает сводку, клиентов, карточку и настройки. При обрыве переподключается сама.

**Доступ.** Все эндпоинты с данными требуют сессии, вход защищён CSRF и ограничен 10 попытками
в минуту. `/metrics` закрыт отдельным токеном `METRICS_TOKEN`: его использует Prometheus,
сессии панели для него недостаточно.

## Пользователи и вход

Регистрации нет: панель внутренняя, пользователей заводит администратор в разделе «Админка» —
логин, имя, фамилия, email и пароль. Там же их блокируют, меняют пароль и выдают права
администратора. Первый администратор создаётся при старте из `DJANGO_SUPERUSER_*` в `.env`.

Первый вход — всегда по логину и паролю.

### Вход через SSO с ключом доступа (OIDC + FIDO2)

Дополнительно можно входить без пароля, ключом доступа (passkey): Touch ID, Windows Hello,
телефон, YubiKey, менеджер паролей. Для этого в Compose есть Keycloak, а панель работает с ним
по OIDC. Включается в `.env`:

```bash
COMPOSE_PROFILES=oidc
OIDC_ENABLED=true
OIDC_PUBLIC_URL=http://localhost:8080      # адрес, по которому открывают панель
OIDC_CLIENT_SECRET=<случайная строка>
KEYCLOAK_PROVISIONER_SECRET=<случайная строка>
KEYCLOAK_ADMIN_PASSWORD=<случайная строка>
```

После `docker compose up -d` на странице входа появится кнопка «Войти через SSO».

1. Пользователь, созданный в «Админке», сразу появляется и в Keycloak.
2. Войдя по паролю, он открывает «Профиль» (клик по имени в шапке) → «Добавить ключ доступа».
   Keycloak подтверждает, что это он, создаёт ключ и возвращает в профиль.
3. Дальше «Войти через SSO» каждый раз спрашивает только ключ.
4. Ключи видны и удаляются в «Профиле». Выход из панели завершает и сессию в Keycloak.

В «Профиле» же список активных сессий: устройство, IP, способ входа, время входа и последней
активности. Любую можно завершить, или все, кроме текущей, разом. Администратор в «Админке»
может завершить все сессии пользователя.

Через SSO пускаются только пользователи, заведённые в панели, уже входившие по паролю и не
заблокированные. Блокировка и смена пароля в «Админке» сразу действуют и в Keycloak.
Пользователей, созданных через Django admin, в Keycloak нет: им SSO включается в «Профиле»
вводом пароля от панели.

WebAuthn работает только по HTTPS или на `localhost`; ключ привязан к адресу панели.
Страницы Keycloak оформлены в стиле панели темой `keycloak/themes/aeza`. Наружу через nginx
открыты только страницы входа Keycloak, его админка — нет. Keycloak работает в dev-режиме с
базой на томе `keycloak-data`; realm из `keycloak/import/churn-realm.json` импортируется только
в пустой том.

Другой OIDC-провайдер: задайте `OIDC_ISSUER_URL`, `OIDC_ISSUER_INTERNAL_URL`, `OIDC_CLIENT_ID`,
`OIDC_CLIENT_SECRET` и разрешите в провайдере redirect URI
`<адрес панели>/api/v1/auth/oidc/callback`. Пути эндпоинтов по умолчанию как у Keycloak, их можно
переопределить через `OIDC_OP_AUTHORIZATION_ENDPOINT`, `OIDC_OP_TOKEN_ENDPOINT`,
`OIDC_OP_USER_ENDPOINT`, `OIDC_OP_JWKS_ENDPOINT`.

## Метрики

```bash
curl -H "Authorization: Bearer <METRICS_TOKEN из .env>" http://localhost:8080/metrics
```

| Метрика | Что значит |
|---|---|
| `churn_customers{level="high\|medium\|low\|none"}` | клиентов по уровням риска |
| `churn_expected_loss_cents` | ожидаемая потеря, центы |
| `churn_revenue_at_risk_cents` | выручка под риском, центы |
| `churn_services_at_risk` | услуг под риском |
| `churn_score_avg` | средний score |
| `churn_last_recalculation_timestamp`, `churn_last_recalculation_duration_seconds` | время и длительность последнего пересчёта |
| `churn_source_rows{kind="accounts\|services\|transactions"}` | сколько строк в загруженных данных |

Prometheus из Compose (`monitoring/prometheus.yml`) собирает метрики каждые 15 секунд с тем же
токеном. Без токена `/metrics` отвечает 401 — так и должно быть.

## Разработка

```bash
docker compose up -d db                 # PostgreSQL на localhost:5433

cd backend
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py load_sample --extended
python manage.py runserver              # http://localhost:8000

cd frontend
npm ci
npm run dev                             # http://localhost:5173, /api проксируется на :8000
npm run dev:mock                        # без backend, на моках MSW
```

Проверки, те же, что в CI:

```bash
cd backend && pytest
cd frontend && npm run lint && npm run build
```

После изменения API перевыгрузите схему: `cd backend && python manage.py spectacular --file openapi.yml`.
CI сверяет её с кодом и не пропустит устаревшую.

GitHub Actions на каждый PR проверяет backend (тесты, миграции, схема), frontend (lint, сборка)
и `docker-compose.yml`. Push в `main` после успешных проверок выкатывает проект на сервер.

## Частые проблемы

- **Порт занят.** Панель слушает 8080, Prometheus — 9090, PostgreSQL — 5433 (меняется через
  `POSTGRES_PORT`). Освободите порт или остановите другой проект.
- **`/metrics` отвечает 401.** Нужен заголовок `Authorization: Bearer <METRICS_TOKEN>`.
- **«Слишком много попыток» при входе.** Сработал лимит, подождите минуту.
- **Странные даты в причинах.** Данные загружали давно: перезагрузите набор командой
  `load_sample --extended`, даты сдвинутся на текущий момент.
- **Нет кнопки «Войти через SSO».** SSO выключен: см. раздел «Вход через SSO».
